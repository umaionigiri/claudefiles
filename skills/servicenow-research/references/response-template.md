# Response Template — 脚注番号方式 (出典は末尾セクションにまとめる)

## 設計原則

**出典のリンクは回答末尾の `## 出典` セクションにまとめる。本文には脚注番号 `[1]` `[2]` のみを置く。**

理由:
- 本文の読みやすさを最大化する (リンクで視覚的にノイズを増やさない)
- それでもどの主張がどのソース由来かは脚注番号で追える (claim-level traceability 維持)
- 同じ出典を複数主張で引く場合に番号で参照できるので、出典セクションが重複しない

## 標準フォーマット

````markdown
## 結論
<主張1>[1]。<主張2>[1][2]。

## 理由 / 背景
<理由文1>[1]。専門用語が出たらインライン括弧で日本語補足を併記する: 例「Business Rule(**レコード操作時に自動実行されるサーバサイドスクリプト**)」。
<理由文2>[3]。

## 具体例 / 手順
1. <手順1>[3]
2. <手順2>[3][4]

```glide
// コード例には説明文 or 直前のコメントで脚注番号を併記
var gr = new GlideRecord('incident'); // [4]
gr.addQuery('state', 1);
gr.query();
```

## 補足 / 注意事項
<注意点>[2]。バージョン依存、ライセンス、関連機能との違いなど。

## 出典
1. [Now Assist for ITSM 概要](https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/markdown/IT%20Service%20Management/now-assist-itsm.md)
2. [関連記事タイトル](https://docs.servicenow.com/...)
3. [手順元の公式ドキュメント](https://raw.githubusercontent.com/...)
4. [GlideRecord API リファレンス](https://developer.servicenow.com/...)

---
*対象リリース: <Australia / Zurich / Yokohama / Xanadu>*
*調査ソース内訳: GitHub ServiceNowDocs (N件), developer.servicenow.com (M件), ...*
*全出典リンクは取得時点で生存確認済 (HTTP 200)*
````

## 脚注番号のルール

| ルール | 詳細 |
|--------|------|
| **1主張1脚注最低保証** | 結論・理由・具体例の各文が事実主張を含むなら最低1つは `[N]` を伴う。一般論や接続文は除外可 |
| **同一出典の重複** | 連続する複数文が同じ出典の場合、最後の文末にだけ付ける (段落単位の括り)。同じ番号は重複させない |
| **複数出典で1主張を裏付け** | `[1][2]` のように番号を連続して書く。番号間にスペース不要 |
| **番号の付与順** | 文書全体を上から走査して、初出順に 1, 2, 3, ... と振る。`scripts/format_response._build_source_registry()` が自動で行う |
| **コード例** | コードブロック内のコメント or 直前/直後の説明文に脚注番号を入れる |
| **「わかりません」ケース** | 出典セクションは出さない (該当ソース無いため)。代わりに「検索済みソース・クエリ・ブランチ」を `## 検索内訳` で明示 |
| **本文中にURL直書き禁止** | 本文には番号 `[N]` のみ。`[title](url)` 形式を本文に置いてはならない (`## 出典` セクション専用) |

## Visual Aids — アイコン / 表 / 図で可読性を高める

長文の散文を避け、以下の視覚要素を積極的に使う。`Claim.text` には複数行 Markdown を埋め込めるので、Python 側の変更は不要。

### アイコン (絵文字) パレット

意味を統一する。ランダムな絵文字選択は逆に読みにくくなるので **以下のセットから選ぶ**:

| アイコン | 用途 | 例 |
|---------|------|-----|
| ✅ | 推奨・正しい例・利点 | `✅ Australia 以降は推奨アプローチ` |
| ⚠️ | 注意点・落とし穴 | `⚠️ Yokohama では non-blocking モードがデフォルト` |
| ❌ | 非推奨・誤った例・避けるべき | `❌ 旧 API は廃止予定` |
| 📌 | 重要事項・ハイライト | `📌 ライセンス必要` |
| 📊 | 統計・メトリクス | `📊 平均応答 200ms` |
| 🔧 | 設定・構成手順 | `🔧 設定例:` |
| 🔗 | 関連機能との連携 | `🔗 Flow Designer と連携` |
| 🆕 | リリースで追加された新機能 | `🆕 Australia で追加` |
| 🗑️ | 削除・廃止された機能 | `🗑️ Yokohama で deprecated` |
| 💡 | Tips・ベストプラクティス | `💡 並列実行で高速化` |
| 🎯 | 目的・ゴール | `🎯 ユースケース:` |
| 📚 | リファレンス・関連ドキュメント | (本文中ではなく `## 出典` の代用ではない、補助的な誘導用) |

**ルール**: 1段落につきアイコンは最大1〜2個まで。多用は避ける。

### 表の活用 (積極推奨)

比較・列挙・パラメータ説明には **必ずテーブルを検討** する。散文より構造化された情報のほうが読み手の認知負荷が低い。

定型パターン:

**機能比較** (リリース間 / 製品間):
```markdown
| 観点 | Australia | Zurich |
|------|-----------|--------|
| 対応スコープ | グローバル / スコープド | グローバルのみ |
| 必要ロール | `now_assist_admin` | `admin` |
| 利用可能API | REST + GraphQL | REST のみ |
```

**パラメータ仕様**:
```markdown
| パラメータ | 型 | 必須 | 説明 |
|----------|----|------|------|
| name | string | ✅ | フィールド名 |
| value | any | ⚠️ 型依存 | 比較対象値 |
```

**手順表** (具体例セクション):
```markdown
| Step | 操作 | 期待結果 |
|------|------|---------|
| 1 | All > MID Servers > New | 新規 MID Server レコード作成画面 |
| 2 | Name 入力 + Save | レコード保存 + 自動的に download URL 表示 |
```

### 図の活用 (ASCII アート)

**重要**: Claude Code は CLI ベースの monospace 描画環境のため、**Mermaid は生のコードブロックとしてしか表示されない**。図を入れる場合は以下の box-drawing 文字を使った ASCII アートに統一する。

許可文字パレット: `┌ ─ ┐ │ └ ┘ ├ ┤ ┬ ┴ ┼ → ← ↑ ↓ ⇒ ⇔ ─ ━`

**Flowchart (ワークフロー / プロセス)**:
```
[Incident 起票] → ┬─→ (High)  → [即時通知] ─┐
                  │                          ├─→ [Assignment Group]
                  └─→ (Low)   → [キュー追加] ┘
```

**Sequence (API 呼び出し / 統合)**:
```
User           ServiceNow        MID Server         顧客環境
 │                │                  │                  │
 │─Discovery 起動→│                  │                  │
 │                │──Probe 命令────→ │                  │
 │                │                  │─SNMP/SSH probe→ │
 │                │                  │← ──── 応答 ──── │
 │                │ ←─── CI データ ──│                  │
 │←─CMDB 更新完了─│                  │                  │
```

**Hierarchy / Tree (階層 / 構造)**:
```
Incident
├── Problem
├── Change Request
│   └── CAB 承認
│       └── Implementation
└── Knowledge Article
```

**Block diagram (システム構成)**:
```
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│  ServiceNow │─REST/MQ→│  MID Server │─SNMP/SSH│ 顧客 ITシス │
│   (Cloud)   │← ─結果─ │  (顧客内)   │← ──応答─│             │
└─────────────┘         └─────────────┘         └─────────────┘
```

**State diagram (状態遷移)**:
```
[New] ──assign──→ [In Progress] ──resolve──→ [Resolved] ──close──→ [Closed]
                       │                          │
                       └──cancel──→ [Cancelled]   └─reopen→ (戻る)
```

ガイドライン:
- 1図につき 80 columns 以内 (CLI 横幅に収める)
- box-drawing 文字以外 (絵文字 / 全角記号など) を図内で混ぜない
- 図は ` ``` ` のフェンスで囲んだコードブロックに入れる (lang指定なし)
- ボックスや矢印が複雑になりすぎる場合は **表に切り替える** ほうが見やすい

### 構造化箇条書き (Markdown lists)

長文の代わりに箇条書きを使う:

```markdown
**主要機能 (Now Assist for ITSM)**:
- ✅ **Incident Summarization** — 過去アクティビティをAIで要約
- ✅ **Resolution Suggestion** — 類似インシデントから対処案を提示
- ⚠️ **Generated Code** — Now Assist for Code は別ライセンス
```

ネストはせいぜい2層まで。3層以上になるなら表に変える。

### 配置ガイドライン

| セクション | 推奨表現 |
|-----------|---------|
| `## 結論` | 短い断定文 + 必要なら 3-5行のコンパクト表で要点列挙 |
| `## 理由 / 背景` | 比較表 / ASCII図 (box-drawing) / 構造化箇条書きを駆使 |
| `## 具体例 / 手順` | 番号付き手順 + 結果列を持つ表 / コードブロック / シーケンス図 |
| `## 補足 / 注意事項` | ⚠️ アイコン + 短い箇条書き |

### 過剰装飾の戒め

- アイコンを文ごとに付けない (情報密度が下がる)
- 1セクションに3個以上の図は入れない (視覚過多)
- 表で十分なところに ASCII 図を使わない (図は関係性の可視化が目的)
- **Mermaid は禁止** — Claude Code CLI で描画されないため
- コード例は 1機能あたり 1ブロックまで (大きなブロックは抜粋に絞る)

## 用語補足の書き方 (平易な日本語ルール)

**初心者でも理解できることを最優先する。** 専門用語・カタカナ英語・略語の多用を避け、まず「何をしているか」を平易な日本語で伝える。技術名はあくまで補助。

補足の対象範囲:

| 範囲 | 例 |
|------|-----|
| ServiceNow 固有の用語 | GlideRecord / Business Rule / Flow Designer / ACL / MID Server / CMDB / Workflow Studio / Now Assist 等 |
| 一般的な技術用語 (重要) | REST API / JSON / OAuth / SPA / WebFetch / SubAgent / allowlist / frontmatter / staging / coalesce 等 |
| 略語 | ITSM / ITOM / GRC / KB / SSO / CI / CD / RAG 等 |

**初出時のみ** インライン括弧で 1〜2 行の平易な日本語説明を入れる:

```markdown
Incident テーブルで Business Rule (**レコード操作時に自動で動くサーバ側プログラム**) を作成し、 ...[1]
```

```markdown
REST API (**HTTP 経由でデータをやり取りする仕組み**) を使って外部システムから取り込み、Import Set 経由で staging (**一時保管領域**) に入れた後、 ...[2]
```

ルール:
- 同じ用語の **2 回目以降は補足不要** (くどさ防止)
- ピリオドや句読点ではなく **括弧の直前にスペースを入れる** (読みやすさのため)
- 補足は **50 字以内 / 1 行** を目安。長くなるなら別段落で説明する
- **完全に一般的な IT 用語** (HTTP / JSON / API のうち広く知られるもの / JavaScript / メール / ファイル / 設定など) は補足不要 (但し迷うときは入れる)
- 「これくらい知っていて当たり前」と思える範囲はかなり狭く取る — 受領者は ServiceNow 初心者かもしれない

`references/glossary.md` に主要用語の補足例集がある。

## 必須セクション

`scripts/format_response.render()` は以下を順に出力する:
1. `## 結論` (1〜3 文)
2. `## 理由 / 背景`
3. `## 具体例 / 手順`
4. `## 補足 / 注意事項` (任意)
5. `## 出典` (番号付き Markdown リンクの列挙)
6. メタフッタ (リリース、ソース内訳、生存確認の旨)

セクションヘッダ名は完全一致でないと eval assertion で fail するので、**「結論」「理由 / 背景」「具体例 / 手順」「補足 / 注意事項」「出典」の表記** を厳守する。

## NG パターン

| NG | 理由 | 直し方 |
|----|------|-------|
| 本文に `[title](url)` 形式の Markdown リンクを書く | 出典は末尾にまとめる規約違反 | 本文では `[N]` 脚注番号のみにし、URL は `## 出典` セクションへ |
| `## 出典` セクションが無い | 末尾まとめ規約違反 | `_render_references_section()` を必ず呼ぶ |
| 出典リンクが allowlist 外 (qiita.com, stackoverflow.com 等) | `Source(...)` で ValueError | 当該情報は破棄、別ソースを探す |
| URL が NotFound (404) | `render(verify_links=True)` で ValueError | URL を修正するか、当該主張ごと削除 |
| バージョン未記載 | フッタに `*対象リリース: ...*` が無い | `Answer(release='australia')` で必ず指定 |
| 専門用語の補足が無い | 初心者要件未達 | 初出語にインライン括弧で 1〜2 行の補足 |
| 主張に脚注番号 `[N]` が無い | trace 不能 | 主張を裏付ける `Source` を `Claim.sources` に追加するか、主張自体を削除 |

## 「わかりません」を返す条件

以下のいずれかに該当する場合、`render()` ではなく `render_unknown()` を呼ぶ:
- 5ソース全てで該当ヒット 0 件
- ヒットはあるが allowlist 外しか無い
- ヒットはあるが URL 生存確認で全て NotFound

`render_unknown()` は検索クエリ・対象ブランチ・調査済みソースを開示する。`## 出典` セクションは出さない (該当無いため)。これにより、ユーザは「本当に存在しない情報」と「クエリの再表現で見つかるかもしれない情報」を判別できる。
