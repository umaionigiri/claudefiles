# Word議事録スキル (word-minutes)

## 前提条件

- Python + python-docx（共有 venv: `~/.claude/skills/.venv`）
- テンプレート: `~/.claude/skills/word-minutes/assets/template.docx`
- Python 実行: `PYTHONUTF8=1 ~/.claude/skills/.venv/Scripts/python.exe`

## 議事録の思想 — スキルを使う前に理解すべきこと

議事録は速記録ではない。会議で話されたことを忠実に書き写すのではなく、**ポイントを整理・構造化した上で書く**。議事録作成者は書記ではなく、会議内容を理解し再構成する専門家である。

### 議事録の4つの役割

1. **関係者への念押し** — アクションプランの担当者にリマインドし、確実に実行に移してもらう
2. **証拠残し** — 決定事項に対して後日異論が出た場合、合意に至った過程を示す
3. **根回し・様子伺い** — 議事録送付とあわせて懸案事項を自然に相談
4. **メンバー育成** — 理解度を確認し認識の齟齬があれば正確な知識を教えられる

この4つの役割を意識して、「誰が読むか」「何のために残すか」を常に考えながら作成する。

### 書くべきでないこと

- **自分たちが不利になること**は書かない。議事録は証跡。後々不利になる書き方はしない
- **「オフレコ」「ここだけの話」**は記述しない
- **参加者を中傷する表現**は使わない（「レベルが低い」→「改善すべき点もあるが」）

### 戦略的テクニック

- **能動態**=やったことをアピール、**受動態**=責任を明示しない場合に使い分ける
- 沈黙肯定で終わった場合でも**「了解した」と記載**する（証跡として必要）
- 会議後に確認できた事項は「※会議後に、XXXであることを確認」と注記付きで記載
- 発言者の「言いたかったこと」と「言ったこと」が違う場合は「言いたかったこと」を記述

| モード | トリガー | 入力 | 出力 |

## Mode 1: 新規作成（create）

### Step 0: 不明情報の事前確認（AskUserQuestion）

**JSON作成の前に必ず実行する。** ユーザーの入力テキストを読み、以下の項目が不足していないかチェックする。
不足している項目がある場合、**AskUserQuestion ツールで一括して確認**する（最大4問）。

#### 確認すべき項目（入力テキストから読み取れない場合のみ質問する）

| 優先度 | 項目 | 質問例 | 選択肢の工夫 |
|--------|------|--------|-------------|
| 高 | 会議の日時 | 「会議の日時はいつですか？」 | 「（未確認）で埋める」+「直接入力する」 |
| 高 | 会議の場所 | 「会議の場所はどこですか？」 | 「（未確認）で埋める」「Teams/オンライン」等 |
| 高 | 作成者（記）・承認者 | 「議事録の作成者（記）と承認者は誰ですか？」 | メモ中の参加者から推測した候補を選択肢に |
| 高 | クライアント組織の正式名称 | 「XX側の正式名称は何ですか？」 | メモ中の略称から推測した候補を選択肢に |
| 中 | 次回ミーティング情報 | — | 不明なら「（未確認）」で埋めてよい |
| 中 | 使用資料名 | — | メモの内容から推測できることが多い |

#### ルール

- **入力テキストから明らかに読み取れる情報は質問しない**（例: 参加者名が全員書かれている場合）
- AskUserQuestion は**最大4問**まで。優先度「高」の不足項目を優先する
- 選択肢には必ず「（未確認）で埋める」を含め、ユーザーが即座に先に進める選択肢を用意する
- 回答が「（未確認）」の場合はそのまま JSON に反映し、生成後に修正可能であることを報告時に伝える

### Step 1: 会議情報の抽出と構造化

ユーザーの入力（会議メモ、チャットログ、箇条書き、テキストファイル）と **Step 0 で得た回答** を統合し、以下を抽出する。

#### 抽出すべき情報

- **ヘッダー**: 作成者、承認者、作成日、承認日、文書タイトル（通常「ミーティング議事録」）
- **基本情報**: 日時、場所、ミーティング・タイトル、出席者、使用資料
- **アジェンダ**: 会議の議題リスト
- **決定事項**: 会議で新たに決まったこと（後述の判断基準に従う）
- **ToDo**: 担当者 + 期限付きのアクション（後述の判断基準に従う）
- **議事詳細**: アジェンダごとに構造化された発言記録
- **次回ミーティング**: 日時、場所、出席者

#### 決定事項の判断基準

決定事項とは「会議の結論として**新たに決定した事項**」:
- 会議の中で議論を経て合意に至った事柄のみを記載する
- 非業務の内容（懇親会の日程等）は含めない
- 当然のこと（クライアントが成果物を確認する等）は含めない
- ただし証拠として残したい場合は含める

#### ToDoの判断基準

ToDoとは「会議中に挙げられた『しなければならないこと』＋担当者＋Due」:
- **会議前から元々やると決めていた事項はToDoにならない**
- ただしクライアント側への念押しとして敢えて書く場合はあり
- 必ず「**誰が**」「**何を**」「**いつまでに**」を明記する
  - NG: 「データを送付する。」
  - OK: 「期限切れの在庫データを関連部門に送付する。」

### よくある判断ポイント

**参加者の情報が曖昧な場合:**
ユーザーが「私とクライアントの田中さん」のように書いた場合、ユーザー側の組織名を確認する。
情報が不十分な場合は「（未確認）」で埋めてファイルを生成し、後から修正できることを伝える。

**アジェンダが明確でない場合:**
メモの内容からトピックを読み取ってアジェンダ項目を整理する。
「その他」「雑談」など議事に含める必要がないものは除外して良い。

**発言者が不明な場合:**
`"speaker": ""` として空にする（括弧は表示されない）。

**リモート参加者:**
名前の後に `(※)` を付ける。例: `"members": "田中(※)、横川（記）"`

**議事担当者（記録者）:**
名前の後に `（記）` を付ける。出席者欄で必ず1名は `（記）` を付与する。

### Step 2: meeting_data.json の作成

#### 議事詳細の level 定義（重要）

各発言の `level` は、会話の構造を表すインデント階層であり、Word の箇条書き記号に直結する。

| level | Word表示 | 意味 | 使うタイミング |
|-------|---------|------|---------------|
| 1 | ● | 新しい論点・報告・質問 | 議題の中で新しいポイントを提示するとき |
| 2 | → | 回答・反応・補足 | level 1 に対する回答・コメント・追加説明 |
| 3 | →（深） | さらなる回答・反応 | level 2 に対する回答・コメント・追加説明 |
| "subtopic" | （インデント付きタイトル） | サブトピック見出し | 議題内の小見出し（例: 課題確認、ToDo状況確認） |

**禁止パターン**: 同一の会話の流れの中で、**発言に対する回答が level 1 になるのはNG**。回答は必ず level 2 以上にする。

```
OK:  ● 質問（ACN） → 回答（OM） → さらに補足（ACN）
OK:  ● 報告A（ACN） ● 報告B（ACN） → 質問（OM） → 回答（ACN）
NG:  ● 質問（ACN） ● 回答（OM）  ← 回答なのに●になっている
```

**判断の目安**:
- 別の話題に移っている → level 1（●）
- 前の発言を受けて反応・回答している → level 2 または 3（→）
- 同じ発言者が連続しても、前の発言の補足・詳細であれば → level 2（→）

#### JSON作成時の文体ルール（必ず守る）

`references/writing-rules.md` を読み込み、以下を適用する:

- **常体（だ・である調）**で統一。「です」「ます」は使わない
- 話し言葉→書き言葉に変換（「見ている」→「把握している」等）
- 固有名詞は略さず正確に。初出の略語は（）で補足
- 時期は明確に（「昨日」→「昨日（7/8）」、「来週」→「来週（7/13w）」）
- 「～について」「～に対して」で文を始めない
- 指示代名詞（これ、それ、あの等）は使わず具体的に書く
- 1文は3行以内（約120文字以内）。長い場合は箇条書きに分割
- 「・」はAND、「/」はOR で使い分ける
- 主語・述語・目的語を省略しない
- ToDo/決定事項タグ: `<ToDo#N （担当者）>` `<決定事項#N>` を議事詳細の該当発言末尾に付与（赤色・太字で表示される）

### Step 3: .docx を生成

```bash
PYTHONUTF8=1 ~/.claude/skills/.venv/Scripts/python.exe \
  ~/.claude/skills/word-minutes/scripts/generate_minutes.py \
  --data meeting_data.json \
  --output OUTPUT.docx
```

ファイル名規則: `YYYYMMDD_クライアント名様_プロジェクト名_会議種別_議事メモ_v01.docx`

例: `20260310_東京交通局様_DX推進_第1回定例_議事メモ_v01.docx`

### Step 4: バリデーション

```bash
PYTHONUTF8=1 ~/.claude/skills/.venv/Scripts/python.exe \
  ~/.claude/skills/word-minutes/scripts/validate_minutes.py OUTPUT.docx
```

全チェック PASS を確認。FAIL があれば JSON を修正して再生成。

### Step 5: セルフチェック（AIによる最終確認）

生成した .docx を読み込み、`references/checklist.md` の19項目を1つずつ確認する。
問題があれば JSON を修正して再生成する。特に以下を重点チェック:

- 決定事項/ToDoが「～する。」で統一されているか
- 議事詳細にToDo/決定事項タグが付与されているか
- 主語・目的語が省略されていないか
- 口語表現が残っていないか

### Step 6: 報告

生成ファイルのパスを伝え、決定事項・ToDoの要約を添える。

## Mode 2: レビュー（review）

### Step 1: 対象ファイル読込

ユーザーが指定した .docx を python-docx で読み込む。

### Step 2: 自動チェック実行

```bash
PYTHONUTF8=1 ~/.claude/skills/.venv/Scripts/python.exe \
  ~/.claude/skills/word-minutes/scripts/review_minutes.py \
  --input INPUT.docx \
  --output REVIEW_RESULT.docx
```

スクリプトが自動検出する項目:
- フォント統一性
- 作成者（記）の有無
- 決定事項/ToDoの文末統一
- 敬体/常体の混在
- 指示代名詞の使用
- 口語表現
- 曖昧な時期表現
- 長文
- 配慮に欠ける表現
- ToDo/決定事項タグの有無

### Step 3: AI追加レビュー

スクリプトでは検出できない項目を、AIが .docx の内容を読んで追加チェックする:

- **内容の構造化**: 時系列ではなく議題に沿って整理されているか
- **論点→結論の対応**: 質問に対する回答が明記されているか
- **ToDoの適切性**: 会議前から決まっていたことが含まれていないか
- **決定事項/ToDoの自己完結性**: 読むだけで意味が通じるか
- **議事内容の理解度**: 曖昧な記述、不正確と思われる記述がないか
- **戦略的観点**: 不利になる記述がないか、了解の記載漏れがないか

### Step 4: レビュー結果の統合報告

スクリプト出力の .docx に加えて、AIが検出した追加指摘を**ユーザーへのテキスト報告**として伝える。
指摘の形式: `【チェック項目名】指摘内容 → 改善案`

## Mode 3: 修正（fix）

### Step 1: 対象ファイル読込

### Step 2: 自動修正実行

```bash
PYTHONUTF8=1 ~/.claude/skills/.venv/Scripts/python.exe \
  ~/.claude/skills/word-minutes/scripts/fix_minutes.py \
  --input INPUT.docx \
  --output FIXED.docx
```

自動修正される項目:
- 口語表現→ビジネス表現（辞書ベース置換）
- 敬体→常体（です→である、ます→る 等）
- 「させて頂く」「頂く」→簡潔な表現
- 「～を行う」→簡潔な動詞
- フォント Meiryo UI 統一

### Step 3: AI追加修正

スクリプトでは対応できない修正を、AIが内容を読んで追加で行う:

- **構造の再整理**: 時系列→議題別に並び替え
- **主語・目的語の補完**: 省略されている箇所を文脈から補う
- **指示代名詞の具体化**: 「これ」「それ」→具体的な名詞に置換
- **ToDo/決定事項タグの追加**: 不足しているタグを議事詳細に付与
- **長文の分割**: 120文字超の文を箇条書きに分割

AI修正後、修正版 .docx を python-docx で更新保存する。

### Step 4: バリデーション + 修正箇所報告

修正版に対して validate_minutes.py を実行し、全チェック PASS を確認。
修正箇所のサマリーをユーザーに報告する。
